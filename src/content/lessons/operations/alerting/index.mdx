<Step id="problem" name="Nobody noticed" tag="PROBLEM">
On Monday morning a customer asks where their weekend orders are. The workflow has been failing since Saturday. Every run is in run history, but nobody was looking.

Monitoring tells you what happened. **Alerts** tell you while it's happening.
</Step>

<Step id="levels" name="Two levels of alerting">
Most teams use two levels (ours):

1. **In the workflow**: a **catch scope** emails the team for each failed run, with the order number and the error. This is what people act on.
2. **Azure Monitor alerts**: a safety net for what the workflow can't report itself, such as a trigger that fails before any run starts, an app that's down, or a catch scope that fails too.

This lesson is about the second level.
</Step>

<Step id="metrics" name="Metrics to alert on">
A Standard logic app exposes workflow metrics in the **App Service standard metrics** namespace. Search for "workflow" to find them, for example:

- **Workflow Runs Failure Rate**, **Workflow Actions Failure Rate**, **Workflow Triggers Failure Rate**
- **Workflow Runs Started Count**, **Workflow Runs Completed Count**
- **Workflow Job Execution Delay**

You can filter them by **Workflow Name** and **Status**. The names differ from Consumption's, so Consumption examples like "Triggers Failed" don't apply.
</Step>

<Step id="rule" name="Create an alert rule">
On the logic app, under **Monitoring**, select **Alerts**, then **Create** > **Alert rule**. Choose:

- a **signal**: one of the workflow metrics (we'd filter it to your workflow);
- a **condition**: for example, greater than or equal to a threshold;
- an **evaluation**: how often the rule **checks** and how far back it looks, for example check every **5 minutes**, look back **15 minutes**. That's how often it looks, not how often you get paged. Pick it by how quickly someone will act (ours): there's no point checking every minute if nobody looks for an hour;
- who gets notified, and how (in Azure Monitor, an action group).

The Microsoft Learn worked example is for Consumption, so check the exact metric name in the portal.

Under **Details** > **Advanced options**, make sure **Automatically resolve alerts** is selected. That makes the alert **stateful**: it resolves when the condition is no longer met. Without it, the alert is stateless and *"fire[s] each time the condition is met, even if alert already fired"*: with a frequent check, that's a new notification every few minutes until it's fixed.
</Step>

<Step id="delay" name="Alert on delay, not just failure" tag="TIP">
Failures aren't the only problem. **Workflow Job Execution Delay** measures the time between a job being scheduled and actually running; the Microsoft Learn docs say the scaler works to keep these delays under control. Our advice: alert on it for workflows where latency matters, such as anything a customer waits for.
</Step>

<Step id="logalerts" name="Log alerts">
A **log alert** runs a Log Analytics query on a schedule and alerts on the result. That fits conditions a metric can't express, such as "any failed action in the Payments workflow". The Microsoft Learn docs have no Standard-specific example, so here's ours, using the table from the monitoring lesson:

```kusto
LogicAppWorkflowRuntime
| where Error != ""
```

**Frequency costs money here.** Microsoft: each log search alert rule *"is billed based on the interval at which the log query is evaluated. More frequent query evaluation results in a higher cost."* A metric alert rule is charged by the number of time series it monitors instead. So for a log alert on a workflow that isn't urgent, check every **15 minutes** or **hourly** rather than every minute (ours).
</Step>

<Step id="health" name="Health Check">
**Health Check** is an App Service feature that keeps traffic away from unhealthy instances. You point it at a small workflow: a **Request** trigger and a **Response** that returns a status from **200 to 299**.

The platform pings that path on every instance once a minute. After **10** failed pings (you can lower it to 2), the instance is taken out of the load balancer; if it stays unhealthy for an **hour**, it's replaced. It needs at least **two instances**, and a path under **65 characters**.
</Step>

<Step id="noise" name="Avoid alert fatigue" tag="TIP">
Our recommendations: alert on **rates** rather than single failures, scope rules to the **workflows that matter**, and route them to whoever is actually on call. An alert that fires every night gets ignored.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- Two levels: a **catch scope** email per failed run, and **Azure Monitor alerts** as the safety net.
- Standard exposes **Workflow Runs/Actions/Triggers Failure Rate**, run counts and **Job Execution Delay**.
- Build **metric alert rules** under Monitoring > Alerts; check metric names in the portal.
- Use **log alerts** for conditions only a query can express.
- **Health Check** removes and replaces unhealthy instances; it needs 2+ instances.
- Alert on rates, for the workflows that matter.
</Step>
