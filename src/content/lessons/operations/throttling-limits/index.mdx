<Step id="problem" name="429 Too Many Requests" tag="PROBLEM">
After a big import, your workflow's runs start failing with **429 Too Many Requests**. Retries help a little, then the backlog grows.

A 429 means *someone* is throttling you. Microsoft describes three places it can happen, and each needs a different fix.
</Step>

<Step id="levels" name="Three levels">
Throttling can happen at:

- **The logic app resource**: your own app hits its limits.
- **The connector**: a managed connector has its own call limits.
- **The destination**: the system you call can't keep up.
</Step>

<Step id="resource" name="Your logic app">
The Microsoft Learn docs list no action-count limit for Standard: a Standard workflow has **no limit on the number of actions** that can run in any interval, where Consumption allows 100,000 per 5 minutes by default (300,000 in high throughput mode).

What you control is **trigger concurrency**: unlimited by default. Turn it on to cap concurrent runs at **1 to 100**, with up to **200 waiting runs**. Remember that turning it on can't be undone. To spot resource-level throttling in Standard, Microsoft points to the **Http 4xx** metric (a general App Service metric that counts all 4xx responses, not only throttling).
</Step>

<Step id="connector" name="The connector">
Every managed connector has **its own limits**, listed on its reference page. The Service Bus connector, for example, allows up to **6,000 calls per minute**.

When a connector returns 429, the action's **retry policy** kicks in, where the action supports one. To go further, Microsoft's options (its examples use Consumption) are **multiple connections** so the workflow can partition the work, a separate connection per action, or changing the **For each** parallelism.
</Step>

<Step id="destination" name="The service you call">
By default, runs, loops and branches all run **in parallel**. Microsoft's example: 20 parallel inserts against a database that allows 15 calls per second. The extra calls fail, retry, and the retries build a backlog that never catches up.

The fixes slow the caller down:
- Put items on a **queue**, and have one workflow do the inserts.
- Split the work into **parent and child** workflows.
- Use **webhook** triggers and actions instead of polling ones.
</Step>

<Step id="storage" name="And the storage account" tag="TIP">
In Standard there's a fourth, quieter limit: the **storage account** behind your app. It throttles beyond 2,000 requests per partition and 20,000 per second per account. Spread the work across workflows, or across multiple storage accounts (up to 32, set up before you create the app). The storage account lesson covers the details.
</Step>

<Step id="sizes" name="Message size limits">
- Without chunking, a message can be up to **100 MB**.
- With **chunking**, an action in Standard can handle up to **1 GB** by default, in chunks of up to **52 MB**.
- Not every connector or API supports chunking, so check before you rely on it.
</Step>

<Step id="apim" name="One Standard-only limit" tag="TIP">
If you call a Standard workflow's Request trigger through the **API Management REST API**, there's a hard limit of **56 calls per 5 minutes**. Call the trigger's **callback URL** instead.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- Throttling happens at the **logic app**, the **connector** or the **destination**.
- Standard has **no action-count limit**; cap runs with **trigger concurrency** (1–100, irreversible).
- Connectors have **their own limits**: retry, use multiple connections, or lower parallelism.
- Protect slow destinations with a **queue**, parent/child workflows or webhooks.
- Messages: **100 MB**, or up to **1 GB** with chunking where supported.
</Step>
