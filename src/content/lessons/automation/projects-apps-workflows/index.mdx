<Step id="problem" name="Keeping automations apart" tag="PROBLEM">
Imagine one team automating order handling and another automating supplier invoices. Without clear boundaries, their connections, settings and workflows get mixed together and are harder to govern as the team grows.

The Microsoft Learn docs describe the same worry: you need to keep applications and their workflows, connections and other items **organized, secure, and separate so that unrelated work doesn't mix together**. This feature is a **preview**, so details can change. The team example is ours.
</Step>

<Step id="levels" name="Three levels">
Azure Logic Apps Automation organizes your work at three levels:

- **Project**: the top-level container that groups applications.
- **Application**: a deployable package that stores workflows, connections, parameters, analytics, settings, and other items.
- **Workflow**: the automation workload itself, with a starting event (**trigger**) and steps (**actions**).

You build from the top down: project first, then application, then workflow.
</Step>

<Step id="project" name="The project">
A project is **an isolated container with its own compute, networking, security, and governance**. The Microsoft Learn docs suggest **one project per team, business area, or scenario**.

You create it in the Azure Logic Apps Automation portal: on the **Projects** tab, select **Create project**, then choose Basic or Advanced (Advanced opens the Azure portal). You provide a subscription, a resource group, a location and a unique project name. Creation **might take several minutes**.

You need an Azure subscription to create projects. Builders who only create workflows need portal access, with **no Azure subscription necessary**.
</Step>

<Step id="members" name="Owner and project roles">
Whoever creates the project becomes its **owner**, a single value that you can't clear or remove. The Microsoft Learn docs say the owner is **a property, not a permission level**. The owner gets Contributor permissions plus the power to delete the project and resources.

You add members in **Settings**, under **Users**, with **Add user**, choosing a role by the principle of least privilege. The project roles are **Reader**, **Author** and **Contributor**. People you add must be in the same Microsoft Entra tenant.
</Step>

<Step id="app" name="The application">
An application is the **deployable and scalable package** inside a project. The Microsoft Learn docs suggest **one application per logical workload or related workflows**, for example `order-processing` or `daily-reports`.

To create one you need the project **Contributor or Author** role; Reader isn't enough. On the **Apps** page, select **Create app**, enter a name and select **Create**. It **might take a minute or two**, so watch the **Status** column and wait until the app is ready before you create connections or workflows.
</Step>

<Step id="privacy" name="Private by default">
Applications are **private by default**. Only the creator, the application owner, can see an app's contents. Project owners and contributors can see **application metadata** for governance, but not workflow content, connections or run history.

To share an app, an application owner or contributor opens the app's **Settings**, then **User permissions**, and adds people. The app roles are **Reader** and **Contributor**. The Microsoft Learn docs say **by design, the Author role is unavailable at the application level**.
</Step>

<Step id="workflow" name="The workflow">
A workflow is **the unit that runs an automation workload**. Each complete workflow:

- lives within an **automation application**
- starts with a **single trigger**, the event that runs it
- follows the trigger with **one or multiple actions**

The workflow quickstart says you need the **Contributor** role to create workflows, while the application quickstart says **Contributor or Author**. The Microsoft Learn docs are inconsistent here, so check your role. The next lesson builds one.
</Step>

<Step id="standard" name="Compared with Standard">
The Microsoft Learn docs map the new levels to things you may know. A **project** is similar to **a Visual Studio Code project that includes one or multiple Standard logic apps and their workflows**. An **application** is similar to **a Standard logic app**. A **workflow** is like other workflows in Standard and Consumption.

So a Standard logic app and an Automation application both package related workflows. The Microsoft Learn docs don't claim they are the same resource type, and neither do we.
</Step>

<Step id="author" name="Author's observation" tag="TIP">
The Microsoft Learn docs don't say where an application runs. In our tests (not in the Microsoft Learn docs), each app became its own **Azure Container App**, the Azure portal showed the project as an **Automation Environment**, and each change to an app created a new version.

These details were seen in one preview environment and can change. The tests are written up in the related article.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Project** is the isolated top-level container: one per team, business area or scenario.
- **Application** is the deployable package: one per logical workload.
- **Workflow** has one trigger and one or more actions, and lives in an application.
- Applications are **private by default**; project roles are Reader, Author, Contributor; app roles are Reader and Contributor.
- Everything is in **preview**, so check the Microsoft Learn docs for changes.
</Step>
