<Step id="problem" name="The API was down" tag="PROBLEM">
At 02:13 your order workflow calls a partner's API, and the partner is in the middle of a deployment. The API answers **503 Service Unavailable**.

By morning the partner is back, but the order is stuck. What did Logic Apps do on its own, what could you have built, and how do you get the order through now?
</Step>

<Step id="retry" name="Retries come first">
Before anything fails, the action **retries**. Most actions use the **default retry policy**: an exponential interval policy with up to **4 retries**.

Retries happen for **408** (timeout), **429** (too many requests) and **5xx** responses, like our 503. If a retry succeeds, the action shows **Succeeded with retries** in run history.

You can switch an action to *Fixed interval*, *Exponential interval* or *None*.
</Step>

<Step id="fails" name="When retries run out">
The partner stays down longer than the retries last. *Call partner API* ends as **Failed**.

*Save order* only runs after *Succeeded*, so it's marked **Skipped**. Nothing handled the failure, so the whole run is **Failed**.
</Step>

<Step id="catch" name="Try and Catch scopes" tag="FIX">
Logic Apps has no try/catch keyword, but **scopes** give you the same pattern. Put *Call partner API* and *Save order* inside a *Scope* named **Try**. Then add a second *Scope* after it, named **Catch**, with your error handling inside: here, an alert to the team.

A scope gets its own status once everything inside it finishes. The Microsoft Learn scopes page says that when any action inside fails, the scope is marked **Failed** (its error-handling page words it as the final action failing). So the Catch scope doesn't need to know which action broke. It only watches the Try scope.
</Step>

<Step id="run-after" name="Configure run after">
What makes Catch a catch is its **run after** setting. Select the Catch scope, open **Settings**, and under **Run after** expand *Try*. Clear **Is successful** and select **Has failed** and **Has timed out**. Add **Is skipped** too if Try can itself be skipped. You must always keep at least one status selected.

In code view, that's the `runAfter` property:

```json
"Catch": {
  "type": "Scope",
  "actions": { ... },
  "runAfter": {
    "Try": ["Failed", "TimedOut"]
  }
}
```

Inside Catch, `result('Try')` returns the results of the Try scope's **top-level** actions (not ones nested in conditions or switches). Filter them for `status` equal to `Failed`, and put their errors in the alert.

<Callout title="Tip">A third scope that runs after Try with **all four** statuses selected runs no matter how Try ended. Use it for cleanup, like a *finally* block.</Callout>
</Step>

<Step id="terminate" name="Keep the run honest">
There's a catch to catching: if a later action **handles** the failure, the run counts as **Succeeded**. Your monitoring would see green.

End the catch scope with a **Terminate** action set to **Failed**, with your own error code and message. The run is now marked failed, but with a clear reason, and the team has already been alerted.
</Step>

<Step id="resubmit" name="Resubmit the run" tag="FIX">
In the morning the partner is back. Open the failed run and select **Resubmit**.

Logic Apps reruns the workflow **with the same inputs** as the original run, and adds it as a **new run** in run history. It uses the **same workflow version** as the original run, even if you've changed the workflow since.
</Step>

<Step id="from-action" name="Resubmit from an action" tag="TIP">
You don't always want to start from the top. **Submit from this action** reruns from a chosen action: actions before it **reuse their original inputs and outputs**, and the selected action and everything after it run again.

It has limits: the run must be finished (Succeeded, Failed or Cancelled), the workflow must be **sequential** with **40 actions or fewer**, and you can't start from a *For each* or *Until* action, from inside or after one, or from inside a Condition or Switch branch.
</Step>

<Step id="duplicates" name="Watch for duplicates" tag="PROBLEM">
Resubmitting runs actions **again**. Microsoft's docs warn that create or delete operations can produce **duplicate data**, or try to delete something that's already gone.

Suppose *Save order* had worked and the failure came later: a full resubmit would save the order twice. Design actions so running them twice is harmless, for example by checking whether the order ID already exists before inserting.
</Step>

<Step id="limits" name="How long you have" tag="TIP">
You can only resubmit a run that's still in **run history**: **90 days** from the run's start by default.

In Standard, **stateless** workflows don't keep run history by default, so there's nothing to resubmit unless you turn run history on for them.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- The **default retry policy** retries 408, 429 and 5xx responses, up to 4 times.
- Wrap risky actions in a **Try scope**. A **Catch scope** that runs after Try *Has failed* or *Has timed out* handles the error, and `result('Try')` shows what failed.
- A handled failure makes the run *Succeeded*; add **Terminate (Failed)** to keep it visible.
- **Resubmit** reruns with the same inputs and workflow version; **Submit from this action** reuses earlier outputs.
- Resubmitting can **duplicate side effects**: make actions safe to run twice.
</Step>
