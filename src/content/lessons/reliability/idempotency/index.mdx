<Step id="problem" name="The same order twice" tag="PROBLEM">
One order, **two shipments**. The same order went through the workflow twice.
</Step>

<Step id="idea" name="The idea">
**Doing it twice should have the same effect as doing it once.**

Like pressing a lift button twice: the lift still comes once. This is called being **idempotent**.
</Step>

<Step id="sources" name="Why it happens">
Repeats are normal:

- Logic Apps delivers a message **at least once**, and rarely twice.
- You **resubmit** a run.
- A **retry** repeats a call that actually worked (ours).
</Step>

<Step id="check" name="Check before you create" tag="FIX">
Before creating the order, look it up:

1. **Get order** by its order number.
2. **Exists already?**
3. **Yes**: stop.
4. **No**: create it and ship.

The second copy finds the first one and stops. This pattern is ours.
</Step>

<Step id="key" name="Look up by order number">
The lookup needs something that is the **same both times**: the **order number**. A new random ID for each attempt would never match.
</Step>

<Step id="sbdedupe" name="Service Bus can help">
Turn on **duplicate detection** on the queue and send the order number as the **message ID**. Service Bus then drops a repeat that arrives within a few minutes (10 by default). Not on the Basic tier.
</Step>

<Step id="unsafe" name="Careful with payments" tag="TIP">
Some calls, like charging a card, can't just be looked up first. Don't retry them blindly: set their retry policy to **None**, and check before you resubmit that run (ours).
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- Repeats happen: delivery, resubmit, retry.
- **Check before you create**, by order number.
- **Service Bus duplicate detection** drops quick repeats.
</Step>
