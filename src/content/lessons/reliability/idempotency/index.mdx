<Step id="problem" name="The same order twice" tag="PROBLEM">
A customer complains: one order, **two shipments**. The same order went through your workflow twice.

Nothing was broken. In integration, **repeats happen**. The fix is to make a repeat do no harm.
</Step>

<Step id="idea" name="The idea: idempotent">
**Doing it twice has the same effect as doing it once.**

Like pressing a lift button twice: the lift still comes once. The Microsoft Learn docs put it this way: after the first execution, duplicate operations don't change the result.
</Step>

<Step id="sources" name="Where repeats come from">
- **Delivery**: Logic Apps delivers a message **at least once**. No messages are lost, and it **rarely** delivers one twice.
- **Resubmit**: rerunning a run repeats its actions, and the Microsoft Learn docs warn it might create **duplicate data**.
- **Retries**: if the first request did reach the service before it timed out, a retry does the work again (ours).
</Step>

<Step id="check" name="Check before you create" tag="FIX">
Build the check into the workflow (our pattern):

1. **Get order** by its order number.
2. **Condition**: does it exist already?
3. **Yes**: stop, there's nothing to do.
4. **No**: *Create order*, then *Ship*.

A second copy of order 4711 now finds the first one and stops. It ships once.
</Step>

<Step id="key" name="Use the order number">
The check only works with something that **stays the same** across repeats: a business key, such as the order number.

The Microsoft Learn docs make the same point for Service Bus message IDs: a GUID works, but anchoring the ID to the business process "yields predictable repeatability". A fresh GUID per attempt would never match.
</Step>

<Step id="sbdedupe" name="Let Service Bus drop repeats">
Service Bus can drop repeats before they reach your workflow. Turn on **duplicate detection** on the queue, and send the order number as the **MessageId**.

A second message with the same MessageId within the window, **10 minutes** by default (20 seconds to 7 days), is accepted and then **ignored and dropped**. The Basic tier doesn't support it.
</Step>

<Step id="unsafe" name="When a call can't be made safe" tag="TIP">
Some calls, like charging a card, can't simply be checked first. If the API supports an **idempotency key**, send the order number. If not, set its retry policy to **None** and think twice before resubmitting that run (ours).
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Idempotent**: twice has the same effect as once.
- Repeats come from **at-least-once delivery**, **resubmits** and **retries**.
- **Check before you create**, keyed on the **order number**.
- **Service Bus duplicate detection** drops repeated MessageIds within a window.
</Step>
