<Step id="problem" name="Fast answer, safe processing" tag="PROBLEM">
When a customer clicks **Buy**, two things must happen: the website must hear **"Order received"** within a second, and the order must **never be lost**.

So the shop uses two workflows in one logic app:

- **Take order**: *Request* → *Check stock* → *Invoke workflow* (hands the order on) → *Response* "Order received".
- **Process order**: *Request* → *Reserve stock* → *Create invoice*.

Each Standard workflow is either **stateful** or **stateless**. These two need different ones.
</Step>

<Step id="stateful" name="Stateful: every step saved">
*Process order* is **stateful**. Each of its steps saves its **inputs, outputs and state to external storage**. That gives you run history, and if a run is interrupted it can be reconstructed from the saved state and run to completion.

Stateful runs can also last much longer: the default maximum run duration is **90 days**. Use stateful when you need to keep, review or reference what happened.
</Step>

<Step id="stateless" name="Stateless: everything in memory">
*Take order* is **stateless**. Its steps keep inputs, outputs and state **in memory only**. Nothing is written to external storage.

Microsoft describes the result as faster performance with quicker response times, higher throughput and reduced running costs, because the run details aren't saved. Stateless workflows run **only synchronously**.
</Step>

<Step id="choose" name="Choose at creation">
You pick **stateful** or **stateless** when you create the workflow, and it stays that way. Microsoft warns that changing the workflow type after creation results in runtime errors.

One Standard logic app can hold both kinds side by side, so *Take order* and *Process order* can live in the same app.
</Step>

<Step id="limits" name="Stateless works best small and short">
Stateless workflows are best for runs **under 5 minutes** (the default maximum run duration) and content **under 64 KB** in total. Bigger content might significantly slow the workflow, or even crash it with out-of-memory exceptions.

Loops are smaller too. By default a *For each* handles **100 items** in a stateless workflow, compared with 100,000 in a stateful one, and an *Until* loop defaults to 60 iterations and allows at most **100**.
</Step>

<Step id="triggers" name="Start with a push trigger">
Microsoft's guidance is that stateless workflows use **push triggers**, which wait for an event instead of running on a schedule: for example *Request*, *Event Hubs* or *Service Bus*.

The **Recurrence** trigger is currently **unavailable** for stateless workflows. You can use managed connector **actions** in a stateless workflow, but the designer doesn't offer managed connector **triggers**. If a workflow has to run on a schedule, make it stateful.
</Step>

<Step id="async" name="No async, no chunking">
Stateless runs are synchronous, so they skip the asynchronous pattern. Say *Check stock* calls a **stock service** that answers **202 Accepted** with a `location` header, meaning "still working, check back here". A stateless workflow **won't poll** that URL. It moves straight on to the next step.

Stateless workflows also don't support **chunking** of large messages. For long-running calls or large content, use stateful.
</Step>

<Step id="history" name="No history, no resubmit" tag="PROBLEM">
A stateless workflow **doesn't store run history** by default, so there's nothing to open when it fails, and only stateful workflows can be **rerun**. If an outage interrupts a stateless run, it **isn't restored automatically**: the caller has to resubmit it.

To debug, switch on **Debug state** in the workflow's settings in the Azure portal. That adds the app setting `Workflows.<workflow-name>.OperationOptions` with the value `WithStatelessRunHistory`; in VS Code you add it to `local.settings.json` yourself. It's meant for debugging only, isn't supported in production, and costs some performance, so turn it off when you're done.
</Step>

<Step id="mix" name="Can stateless call stateful?" tag="TIP">
Yes. That's the arrow between the two frames. *Take order* uses the built-in action **Workflow Operations - Invoke a workflow in this workflow app** to call *Process order*:

1. *Process order* answers straight away with **202 Accepted**, meaning "got it".
2. *Take order* **doesn't wait** for the order to be processed. It goes on to *Response* and tells the website "Order received".
3. *Process order* reserves the stock and creates the invoice on its own, and every step is **saved**.

Microsoft calls this the **synchronous ("fire and forget")** pattern. The other way round, a workflow that calls a **stateless** one **waits** for its answer.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Stateful** saves inputs, outputs and state to storage: run history, resubmit and long runs.
- **Stateless** keeps everything in memory: faster and cheaper to run, synchronous only.
- The choice is made **at creation**. One logic app can hold both.
- Stateless works best **under 5 minutes and 64 KB**, starts from **push triggers** (no Recurrence, no managed connector triggers), and has no async polling or chunking.
- No run history and no rerun by default: turn on **Debug state** (`WithStatelessRunHistory`) only while debugging.
</Step>
