<Step id="problem" name="Where's my order?" tag="PROBLEM">
A customer says their order never arrived. The website sent it to your Logic Apps workflow, the workflow should have put it on the orders queue, and the warehouse never saw it.

Before you can find out what went wrong, you need to know what happens to a single order as it moves through a workflow run. Let's follow one.
</Step>

<Step id="listen" name="Two ways to listen">
Every workflow starts with a **trigger**. Triggers come in two styles.

A **push trigger** waits to be called. The *Request* trigger creates an HTTPS endpoint, and the workflow starts when someone (here, the shop website) sends a request to it.

A **polling trigger** checks a service on a schedule, for example every minute: "is there a new file in this SFTP folder?"
</Step>

<Step id="skipped" name="Nothing new: skipped">
When a polling trigger checks and finds nothing that matches, its trigger history shows **Skipped**.

No run is created for a skipped trigger. So if your workflow "didn't run", the trigger history is the first place to look: maybe it ran its check and simply found nothing.
</Step>

<Step id="fired" name="The trigger fires">
Back to our order. The website posts it to the Request trigger, the trigger **fires**, and Logic Apps creates a new **workflow instance**: a run.

That run carries its own copy of the trigger's outputs, the order, and has its own status from now until it finishes.
</Step>

<Step id="actions" name="Actions run in order">
By default, actions run **one after another**. Each action has a `runAfter` setting that says which earlier action it waits for, and in which status.

The default is: run only if the previous action **Succeeded**. *Parse order* finishes, then *Check stock* starts, then the order goes onto the queue.
</Step>

<Step id="history" name="Every step is recorded">
While the order moves, Logic Apps records it at two levels:

1. **The run**: one run for each time the trigger fires, in the **run history**, with its status and when it started and ended.
2. **Every step**: the trigger and each action get their own record, with status, timing, **inputs**, **outputs** and any error. For our order that's the **Request** itself (the order that came in), then *Parse order*, *Check stock* and *Send to queue*.

In the portal you see the trigger's inputs and outputs in the **trigger history**. In storage, the request is kept the same way as the actions: Standard keeps these records in Azure Storage tables, linked to blobs that hold the inputs and outputs (author's observation; Daniel's storage article shows the tables).

Run history is kept for **90 days** by default, in both Consumption and Standard, and you can change that.

<Callout title="Standard only" variant="info">Stateless workflows in Standard don't keep run history by default. They trade it for speed. Stateful workflows do.</Callout>
</Step>

<Step id="parallel" name="Many runs at once">
A second order arrives from the mobile app while the first is still running. It doesn't wait: each trigger fire gets its own run, and **by default runs execute in parallel**, with no limit.

You can turn on trigger concurrency control to cap how many runs execute at once.

<Callout title="Watch out">Once you turn concurrency control on, you can't turn it off again for that trigger.</Callout>
</Step>

<Step id="failure" name="One action fails" tag="PROBLEM">
Now our customer's run. *Check stock* calls the stock system and gets an error. The action is marked **Failed**.

The next action only runs after *Succeeded*, so *Send to queue* is marked **Skipped**, and because a step failed, the whole run ends as **Failed**. That's why the warehouse never saw the order.
</Step>

<Step id="read" name="Reading the run history" tag="TIP">
Open the run in the run history and you see each step's status:

- The **run**: **Failed**, because at least one action failed.
- *Request* and *Parse order*: **Succeeded**.
- *Check stock*: **Failed**. Its inputs and outputs show the call that was sent and the HTTP 500 that came back.
- *Send to queue*: **Skipped**. When an action fails, the action after it is marked Skipped, so it never ran.

Run statuses you'll see: *Running*, *Succeeded*, *Failed*, *Cancelled*, *Timed out*, *Waiting* and *Aborted*. Actions can also be *Skipped* or *Succeeded with retries*.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- A **trigger** starts everything: push triggers wait to be called, polling triggers check on a schedule.
- A skipped trigger creates **no run**. A fired trigger creates **one run**.
- Actions run **in order**, each waiting for the previous one to *Succeed* unless you change `runAfter`.
- A failed action makes the steps after it **Skipped** and the run **Failed**.
- **One run per trigger fire**, and a record for **every step**, the request included, with its inputs and outputs. Kept 90 days by default.
</Step>
