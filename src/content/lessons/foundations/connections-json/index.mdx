<Step id="problem" name="It worked on my laptop" tag="PROBLEM">
Your workflow sends messages to Service Bus and email through Office 365. It runs fine in VS Code. You deploy it to Azure, and the Office 365 action fails to connect.

The answer is in one file you may never have opened: **connections.json**.
</Step>

<Step id="what" name="One file for connections">
`connections.json` is part of your Standard project, next to `host.json` and your workflow folders. It holds the **metadata, endpoints and keys** for the managed connections and Azure Functions your workflows use, plus the settings for built-in connections.

You rarely write it by hand: when you use the designer in VS Code, the runtime **generates the connection metadata** in this file for you.
</Step>

<Step id="kinds" name="Three kinds of connection">
The file has a section for each kind of connection, and each has its own JSON shape:

- **`serviceProviderConnections`**: built-in connectors, such as the built-in Service Bus.
- **`managedApiConnections`**: managed connectors, such as Office 365.
- **`functionConnections`**: calls to Azure Functions.

Microsoft notes why the shape matters: **endpoints change when you move between environments**.
</Step>

<Step id="builtin" name="A built-in connection">
A built-in connection keeps its settings in the file, and its secret in an **app setting**:

```json
"serviceProviderConnections": {
  "serviceBus": {
    "parameterValues": {
      "connectionString": "@appsetting('servicebus_connectionString')"
    },
    "serviceProvider": { "id": "/serviceProviders/serviceBus" },
    "displayName": "serviceBus"
  }
}
```

A workflow action uses it by name: its `serviceProviderConfiguration` has `"connectionName": "serviceBus"`.
</Step>

<Step id="managed" name="A managed connection">
A managed connection is different: the connection itself is a **separate Azure resource**, an API connection of type `Microsoft.Web/connections`, deployed with your infrastructure, for example in an ARM template. `connections.json` points at it. This example is adapted from Learn's Service Bus and SQL examples:

```json
"managedApiConnections": {
  "office365": {
    "api": { "id": "/subscriptions/.../managedApis/office365" },
    "connection": { "id": "/subscriptions/.../connections/office365" },
    "connectionRuntimeUrl": "@appsetting('office365-ConnectionRuntimeUrl')",
    "authentication": { "type": "ManagedServiceIdentity" }
  }
}
```
</Step>

<Step id="local" name="Local isn't Azure" tag="PROBLEM">
When VS Code creates a managed connection, it's **for local use**. Its authentication is a **raw key** stored in `local.settings.json`, and Microsoft says these keys are for development only: they **expire after seven days**.

So before you release to Azure, change the connection's authentication to the Azure format, a **managed identity**. And every managed API connection needs an **access policy** that gives your logic app's identity permission to use it. A missing access policy, or leftover local authentication, is a likely cause of "it worked on my laptop".
</Step>

<Step id="identity" name="Managed identity" tag="FIX">
In Azure, a **managed identity** is the default and recommended way to authenticate managed connections: `"type": "ManagedServiceIdentity"`.

Each Standard logic app has a **system-assigned identity** enabled by default, and uses it to authenticate its connections. If you disable it, connections stop working. To use a user-assigned identity instead, add an `identity` property with its resource ID to the connection's `authentication` object.
</Step>

<Step id="params" name="Parameterize per environment">
To deploy the same project to test and production, **parameterize** `connections.json`. Only two expression types are allowed in it: `@parameters(...)` and `@appsetting(...)`. Replace literals such as `connectionRuntimeUrl` with one of them.

<Callout title="Watch out">A parameterized `connections.json` restricts the designer, locally and in the portal. Microsoft suggests developing with a non-parameterized file, and swapping in the parameterized one in your deployment pipeline.</Callout>
</Step>

<Step id="secrets" name="Where secrets go" tag="TIP">
Notice that Microsoft's examples never put a secret in `connections.json` itself: connection strings and keys come from **app settings** through `@appsetting(...)`. In Azure, app settings can reference **Azure Key Vault**.

Locally, those values live in `local.settings.json`, which can contain secrets, so **keep it out of source control**. It isn't deployed anyway.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- `connections.json` holds managed and function connection metadata, plus the settings for built-in connections.
- Three sections: **service provider** (built-in), **managed API** and **function** connections.
- Built-in connections live in the file; managed ones point at a separate **API connection** resource.
- Local raw keys expire after 7 days: switch to **managed identity** and add **access policies** for Azure.
- Parameterize with `@parameters` and `@appsetting` only; keep secrets in app settings, not the file.
</Step>
