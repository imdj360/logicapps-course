<Step id="problem" name="Two sides of MCP" tag="PROBLEM">
The **Model Context Protocol (MCP)** is a standard way for AI agents to discover and call tools without custom glue code.

With Azure Logic Apps, you use MCP in **two directions**:

1. **Expose** your tested Logic Apps workflows as an **MCP server** so external agents can call them.
2. **Call** external **MCP servers** from a Logic Apps workflow using the MCP connector inside an **Agent Loop** (ours: the Microsoft Learn docs don't cover this side yet).
</Step>

<Step id="expose" name="Expose: Logic App as an MCP server">
A **Standard** logic app can act as a remote **MCP server** (preview): each workflow you pick becomes a discoverable tool for MCP clients. The Microsoft Learn docs test it from **GitHub Copilot in Visual Studio Code**.

In the Azure portal, open your Standard logic app and go to **Agents > MCP servers**. You can host several logical MCP servers in one logic app, each grouping related workflows.
</Step>

<Step id="requirements" name="What an exposed workflow needs">
To expose a workflow as an MCP tool, it must:

- start with a **Request** trigger (*When an HTTP request is received*);
- end with a **Response** action;
- run in a **Workflow Service Plan** or **ASE v3**.

Add a clear **trigger description** and **Request Body JSON Schema** (with parameter descriptions and `required` fields). Agents rely on those descriptions to decide when and how to call your tool.
</Step>

<Step id="auth" name="Secure & connect to your MCP server">
Standard MCP servers use **OAuth 2.0** by default (via **Easy Auth** and a Microsoft Entra app registration; note that Learn's MCP OAuth setup sets Easy Auth to allow unauthenticated requests through to the endpoint). You can also use **API keys**.

They support **Streamable HTTP** out of the box and **Server-Sent Events (SSE)** (which needs VNet integration and a `host.json` cross-worker setting).
</Step>

<Step id="apicenter" name="Other expose routes: API Center & Foundry">
- **Azure API Center** (preview): expose a single **managed connector** as an MCP server backed by a Standard logic app (one action per tool; built-in and custom connectors aren't supported).
- **Microsoft Foundry** (preview): Foundry agents can also call Request/Response Logic Apps workflows directly as tools, including workflows that wait for a human approval.
</Step>

<Step id="call" name="Call: Logic App as an MCP client">
Now flip the direction. Your own Logic App has an **Agent Loop** and needs tools that already live on an **external MCP server** — a third-party service, a Microsoft MCP server, or another team's server.

Instead of hand-wiring raw HTTP actions for every endpoint, add an **MCP server** connection (the MCP client connector) directly to your Agent Loop and point it at the remote server's URL.

The Microsoft Learn docs don't document this side yet. These steps come from hands-on testing (see the related article under References), so treat them as **ours**.
</Step>

<Step id="discover" name="How the Agent Loop calls MCP">
Once connected, the Agent Loop handles the MCP protocol for you (ours, from hands-on testing):

1. **Initialize** the MCP session with the remote server.
2. **Discover (`tools/list`)** the available tools, descriptions and input schemas at runtime.
3. **Call (`tools/call`)** whichever tool the model picks, feeding the result back into the loop until it finishes.

Because tools are listed at runtime, a tool the remote server adds or updates is picked up on the next run (ours).
</Step>

<Step id="filter" name="Auth & allowed tools on the client" tag="TIP">
Pass the remote server's authentication (API key or OAuth/Bearer token) on the MCP connection (ours).

If a remote MCP server exposes dozens of tools, restrict **Allowed Tools** to just the ones your agent actually needs (ours). That saves context tokens, speeds up decisions and prevents the agent from calling risky tools by mistake.
</Step>

<Step id="both" name="Put both together: Logic App to Logic App" tag="TIP">
Because Logic Apps can both **expose** and **call** MCP, teams can cleanly split responsibilities (ours):

- **Domain teams** publish their tested workflows as a Standard **MCP server**.
- **Agent teams** connect their **Agent Loop** to that server via the **MCP connector**.

Business logic stays versioned and reusable in one place, while multiple agents share the same governed toolset.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Expose (MCP server):** Standard logic app (**Agents > MCP servers**, preview) turns Request/Response workflows into tools over Streamable HTTP or SSE, secured with OAuth (Easy Auth) or keys.
- **Describe well:** trigger descriptions and JSON schemas guide how agents pick and call your tools.
- **Call (MCP client, ours):** add a remote MCP server to an **Agent Loop** via the MCP connector to discover (`tools/list`) and invoke (`tools/call`) external tools dynamically. Not yet in the Microsoft Learn docs.
- **Scope it:** configure auth and limit **Allowed Tools** to keep agents fast and safe.
</Step>
