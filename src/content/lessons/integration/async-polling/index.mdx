<Step id="problem" name="Someone is waiting" tag="PROBLEM">
The website calls your **Place order** workflow and waits for an answer. The workflow runs three steps in order: **Request** (the order comes in), **HTTP** (call the partner to confirm) and **Response** (answer the website). The partner can take minutes.

Two questions follow: how long can the website wait for you, and how long can you wait for the partner?
</Step>

<Step id="sync" name="Request and Response">
A **Request** trigger with a **Response** action is the **request-response** pattern: the website waits until the workflow reaches the Response, so it waits for the partner call too.

The workflow keeps the inbound request open only for a limited time: **225 seconds** in Standard (120 in Consumption). If no Response is sent by then, the caller gets **504 Gateway Timeout**. If every Response action is skipped, the caller gets **502 Bad Gateway**, even if the run succeeds.
</Step>

<Step id="asyncin" name="Switch 1: on the Response">
This switch faces the **website**. Turn on **Asynchronous response** on the **Response** action, or leave out the Response action, and the website immediately gets **202 Accepted**. The workflow carries on with the partner call, and can take as long as it needs, within a stateful workflow's run duration.

The caller then needs another way to learn the outcome, for example a callback or a status it can check. The Microsoft Learn docs don't prescribe one.
</Step>

<Step id="outbound" name="Switch 2: on the HTTP action">
A different switch, facing the **partner**: **Asynchronous pattern** on the **HTTP** action. In a **stateful** workflow it's on by default. If the API answers **202 Accepted** with a **location** header, the engine **polls** that URL until it gets a response other than 202.

You find it in the HTTP action's settings under **Networking**. The API can slow the polling down with a **Retry-After** header.

Don't mix them up: **Asynchronous response** (Response action) is about answering the website; **Asynchronous pattern** (HTTP action) is about waiting for the partner.
</Step>

<Step id="build" name="Building a pollable API" tag="TIP">
If you build the API yourself, follow the pattern: answer **202 Accepted** with a **location** header (required) and optionally **Retry-After**. While the job runs, keep answering 202 at that location; when it's done, answer **200 OK** with the result.

By default, Logic Apps polls the location after **one second**.
</Step>

<Step id="nolocation" name="202 without a location" tag="PROBLEM">
Some APIs answer 202 with no location header to poll. For those, turn **off** the HTTP action's Asynchronous pattern setting, so, in our view, the action doesn't keep checking for a status that never comes. The Microsoft Learn docs' own reasons to turn it off are to stop checking location headers and to avoid HTTP timeouts on long-running tasks.
</Step>

<Step id="stateless" name="Stateless doesn't poll">
In a **stateless** workflow, HTTP actions don't use the asynchronous pattern. They run synchronously, return the **202 as-is**, and move on: a location header isn't polled.

If you need polling, use a stateful workflow.
</Step>

<Step id="webhook" name="Webhooks instead of polling">
Polling means asking "done yet?" over and over. A **webhook** turns it around: the **HTTP Webhook** action calls the service's **subscribe** endpoint with a **callback URL**, and the workflow **pauses** until the service posts to that URL. Then it unsubscribes.

It needs a service that supports subscribe and unsubscribe, but nothing polls in the meantime. In Standard, a webhook waits up to **30 days** in a stateful workflow and **5 minutes** in a stateless one.
</Step>

<Step id="timeouts" name="Timeouts to know" tag="TIP">
- An outbound HTTP request in Standard times out after **225 seconds** by default; you can lower it per action under **Request options** or in host settings, but 225 seconds is also the maximum.
- For longer operations, Microsoft suggests the **asynchronous polling** pattern or an **Until** loop.
- A stateful run can last **90 days** by default; a stateless one **5 minutes**.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Request + Response** is synchronous: up to **225 s** in Standard, then **504**.
- **Asynchronous response**, on the **Response** action: the website gets **202** at once.
- **Asynchronous pattern**, on the **HTTP** action: the workflow polls a **202 + location** partner until it's done.
- **Stateless** workflows don't poll.
- **HTTP Webhook** waits for a callback instead of polling.
</Step>
