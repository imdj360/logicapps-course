<Step id="problem" name="The order endpoint is public" tag="PROBLEM">
The order-intake workflow starts with a **Request** trigger. Its URL works from anywhere on the internet.

Security's rule: only systems on the company network may call it.
</Step>

<Step id="idea" name="The idea">
**A private endpoint gives the logic app a private IP address inside your virtual network.**

Microsoft describes it as a network interface that effectively brings the service into your network. Callers on the network use that address; from outside the network, calls get 403 Forbidden.
</Step>

<Step id="inbound-only" name="Inbound only">
A private endpoint changes only **inbound** calls. Microsoft notes that enabling it doesn't affect outbound traffic, which still flows through the App Service infrastructure. For outbound, use **VNet integration** (the previous lesson).

The private endpoint needs a subnet **without delegations**.
</Step>

<Step id="setup" name="Add the private endpoint">
The workflow needs a built-in trigger that receives requests, such as **Request** or **HTTP + Webhook**.

1. On the logic app, go to **Settings** > **Networking**.
2. In **Inbound traffic configuration**, select the link next to **Private endpoints**.
3. Select **Add** > **Express** or **Advanced**, and fill in the endpoint details.
</Step>

<Step id="test" name="403 means it works">
Call the workflow URL again from outside the network: you now get **403 Forbidden**. Microsoft calls that the expected result: the private endpoint is set up and working.

To test the real path, call it from inside the network, for example from a virtual machine in the same virtual network.
</Step>

<Step id="breaks" name="What stops working" tag="PROBLEM">
Microsoft lists the side effects:

- **Managed webhook triggers and actions** don't work, such as the **Event Grid** and **Dataverse** triggers. They run in the public cloud and can't call into your private network.
- The **Office 365 Outlook** trigger fires only **hourly**.
- From outside the network, **monitoring view** can't show trigger and action inputs and outputs.
</Step>

<Step id="deploy" name="Deploying a private app">
Deployment from **VS Code** or the **Azure CLI** works only from **inside** the virtual network.

From outside, use the **Deployment Center** to link the logic app to a **GitHub** repo and let Azure build and deploy it. For that to work, remove the `WEBSITE_RUN_FROM_PACKAGE` app setting or set it to `0`.
</Step>

<Step id="restrictions" name="Or keep it public, but filtered" tag="TIP">
If a private endpoint is too much, **access restrictions** under Networking can allow or deny address ranges, a feature inherited from App Service. For Standard, the same access restrictions also control who can view **run history** inputs and outputs. Note that access restrictions **don't apply** to traffic that comes in through a private endpoint.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- A **private endpoint** puts the app's inbound address inside your network; outbound is unaffected.
- Add it under **Networking** > **Inbound traffic configuration**; from outside you get **403**.
- **Managed webhook** triggers stop working; the **Outlook** trigger goes hourly; monitoring hides inputs and outputs from outside.
- Deploy from inside the network, or through the **Deployment Center** with `WEBSITE_RUN_FROM_PACKAGE` removed or `0`.
- Lighter option: **access restrictions** on the public endpoint.
</Step>
