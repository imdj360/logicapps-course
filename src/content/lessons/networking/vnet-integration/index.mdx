<Step id="problem" name="The API has no public address" tag="PROBLEM">
The order workflow must call the **warehouse API**. It runs inside the company's virtual network at **10.0.1.3** and has no public address.

The workflow's HTTP action calls 10.0.1.3, and it fails. Microsoft's own walkthrough calls that expected: the workflow runs in the cloud and can't reach your internal service.
</Step>

<Step id="idea" name="The idea">
**VNet integration routes the logic app's outbound calls through a subnet in your virtual network.**

Think of it as giving the logic app a desk inside the office network (ours): it still lives in Azure, but the calls it makes now start from inside.
</Step>

<Step id="outbound-only" name="Outbound only">
VNet integration affects **only outbound** traffic: calls the logic app makes.

Calls *into* the logic app still arrive on its shared public endpoint. Taking that off the internet is a separate feature, the **private endpoint**, which the next lesson covers. The two are independent, and you can use either or both.
</Step>

<Step id="setup" name="Turn it on">
1. On the logic app, go to **Settings** > **Networking**.
2. In **Outbound traffic configuration**, select **Virtual network integration** > **Add virtual network integration**.
3. Pick the subscription, the virtual network that reaches the warehouse API, and the subnet. Select **Connect**.

Run the workflow again. The same HTTP action to 10.0.1.3 now succeeds.
</Step>

<Step id="subnet" name="Size the subnet once" tag="TIP">
You **can't change the subnet size** after you assign it, so plan for the scale the app might reach.

Microsoft recommends a **/26** subnet (64 addresses). If you create it in the Azure portal, **/27** is the minimum. A busy logic app can scale out to many instances, and each one needs an address.
</Step>

<Step id="route-all" name="All outbound goes through the VNet">
By default, the **Outbound internet traffic** option is selected, so **all** outbound traffic from the app goes through the virtual network, not just calls to private addresses. In that case the `WEBSITE_VNET_ROUTE_ALL` app setting is ignored.

So your network's firewall, network security groups (NSGs) and route tables (UDRs) now apply to everything the app calls.
</Step>

<Step id="connectors" name="Which connectors use the VNet">
- **Built-in** operations run inside the logic app, so their calls go through the VNet. That's why the **HTTP** action reached 10.0.1.3. Built-in service provider connectors, such as **SQL Server**, can reach private and on-premises data sources this way **without the on-premises data gateway**.
- **Managed** connectors run in Azure, outside your network. The app talks to the managed API service, so if an NSG, UDR or firewall controls outbound traffic, allow outbound connections to **all managed connector IP addresses** in your region. Otherwise managed connectors stop working.
</Step>

<Step id="dns" name="Your own DNS" tag="TIP">
If your virtual network uses its own DNS server, add the app setting `WEBSITE_DNS_SERVER` with its IP address, and `WEBSITE_DNS_ALT_SERVER` for a secondary one.

One more dependency: the runtime needs an uninterrupted connection to its **storage account**. If that storage is private too, specific ports must be open. A later lesson in this module covers it.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- By default a workflow can't reach a private IP: it runs in the cloud.
- **VNet integration** sends the app's **outbound** calls through a subnet in your network. Inbound needs a **private endpoint** (next lesson).
- Use a **/26** subnet; you can't resize it later.
- By default **all** outbound traffic goes through the VNet.
- **Built-in** operations use the VNet; **managed** connectors need their regional **IP addresses** allowed.
- Own DNS: `WEBSITE_DNS_SERVER`.
</Step>
