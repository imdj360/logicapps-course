<Step id="problem" name="Storage must go private too" tag="PROBLEM">
Security's next rule: **no storage account with public access**.

But a Standard logic app **requires** a storage account for its artifacts. Block public access the wrong way and the app can't load its workflows at all.
</Step>

<Step id="idea" name="The idea">
**Give the storage account private endpoints in your virtual network, and let the logic app reach them through VNet integration.**

The app's own storage traffic then stays inside your network, like its other outbound calls.
</Step>

<Step id="four" name="Four endpoints, not one">
Azure Storage has separate services, and Microsoft says to create **different private endpoints for each**: **Table**, **Queue**, **Blob** and **File**.

The Hosting & runtime module explains what the runtime keeps in each.
</Step>

<Step id="portal" name="Portal or VS Code: public first">
Deploying from the portal or VS Code needs **temporary public access** to the storage account:

1. On the storage account, under **Networking**, allow access from **All networks**.
2. Deploy the logic app.
3. Add **VNet integration** to the virtual network with the storage private endpoints.
4. Add the app setting `WEBSITE_CONTENTOVERVNET` = `1`, plus `WEBSITE_DNS_SERVER` if you use your own DNS.
5. Switch the storage account to **Selected networks**, adding your virtual networks.

The switch can interrupt the app, and workflows can **temporarily disappear**. If they do, restart the logic app and wait several minutes.
</Step>

<Step id="arm" name="ARM template: never public">
If policy doesn't allow even temporary public access, deploy with an **ARM template**. Microsoft's example creates:

- a storage account that **denies public traffic**;
- a virtual network and subnets;
- **private DNS zones and private endpoints** for Blob, File, Queue and Table;
- a **file share** for the runtime;
- a **WS1** plan and a logic app with **VNet integration**.

One exception: the portal can deploy to an **App Service Environment** even when the storage is private, as long as the two subnets can reach each other.
</Step>

<Step id="ports" name="Open the right ports" tag="TIP">
The runtime needs an uninterrupted connection to its storage. From the subnet integrated with the logic app, allow:

- **443** to the storage account;
- **445** to the storage account, for the SMB file share;
- **20000–30000** between the logic app's own worker nodes.
</Step>

<Step id="errors" name="When the app can't reach storage" tag="PROBLEM">
Microsoft lists errors that mean the app can't reach its storage, for example:

- *Access to the path 'C:\home\site\wwwroot\host.json' is denied*
- *The network path was not found*
- *Encountered an error (ServiceUnavailable) from host runtime*: the workflows don't load.

The app isn't running then, so the Kudu console can't help.
</Step>

<Step id="fix" name="How to find the cause">
1. Check that the storage account and file share still exist.
2. Check the app settings `WEBSITE_CONTENTAZUREFILECONNECTIONSTRING` and `WEBSITE_CONTENTSHARE` point at the right account and share.
3. Under **Diagnose and solve problems**, run **Logic App Down or Reporting Errors** and **Network Troubleshooter**.
4. From a VM in another subnet of the same virtual network, try to reach the storage account, for example with Storage Explorer.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- The storage account is **required**; make it private with endpoints for **Table, Queue, Blob and File**.
- **Portal / VS Code**: temporary public access, then VNet integration, `WEBSITE_CONTENTOVERVNET=1`, then lock it down.
- **ARM template**: no public access at any point.
- Open **443**, **445** and **20000–30000** from the integrated subnet.
- Errors about `host.json`, the network path or *ServiceUnavailable* point at storage access.
</Step>
