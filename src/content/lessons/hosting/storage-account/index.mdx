<Step id="problem" name="Slow, but not busy" tag="PROBLEM">
At peak, your order runs slow down. The instances' CPU is fine and the plan isn't maxed out. So what's the bottleneck?

Often it's the one resource nobody looks at: the **storage account** behind the logic app.
</Step>

<Step id="what" name="What goes into storage">
Stateful workflows use Azure Storage for everything they keep:

- **Tables** for persistent data while runs execute.
- **Blobs** for run history. In practice that means the **inputs and outputs of each action**: the action rows in Tables link to them (ours, from the related storage article).
- **Queues** for scheduling, such as trigger operations.

Every action in a stateful run reads and writes here. Stateless workflows keep their state in memory instead.
</Step>

<Step id="setting" name="AzureWebJobsStorage">
The connection to that account is the app setting `AzureWebJobsStorage`, and it's **required**. In the `local.settings.json` that VS Code creates on Windows, it's set to `UseDevelopmentStorage=true`; on macOS and Linux, the Microsoft Learn sample uses a real storage account connection string.

When you publish a new Standard logic app from VS Code, it creates the required resources, such as a storage account.
</Step>

<Step id="limits" name="Storage has limits" tag="PROBLEM">
A single storage account handles up to **2,000 requests per partition** and **20,000 requests per second** at the account level. Beyond those, requests are **subject to throttling**.

A busy stateful logic app makes many storage requests for every run, so a burst of orders can hit those limits while CPU stays idle.
</Step>

<Step id="spread" name="Spread the load" tag="FIX">
The first step is to **distribute work across multiple workflows**. When one account isn't enough, plan for about **100,000 action executions per minute per storage account** (fewer if your actions are compute-heavy), and add more accounts.
</Step>

<Step id="scaleunits" name="Up to 32 storage accounts">
A Standard logic app can use up to **32 storage accounts**. Set `Runtime.ScaleUnitsCount` in `host.json` to the number of accounts, and add one connection string per account as an app setting: `CloudStorageAccount.Workflows.ScaleUnitsDataStorage.CU00.ConnectionString`, then `CU01`, `CU02` and so on. `AzureWebJobsStorage` uses the same connection string as `CU00`.

<Callout title="Watch out">Set this up **before** you create the logic app. Microsoft warns that if you change these settings later, you might lose data or not get the scale you need.</Callout>
</Step>

<Step id="retention" name="How long runs stay">
Run history stays in storage for **90 days** by default. You can change that with the app setting `Workflows.RuntimeConfiguration.RetentionInDays`, from **7 to 365** days, or per workflow.

The cleanup job checks for old runs every **7 days** by default (host setting `Runtime.FlowMaintenanceJob.RetentionCooldownInterval`), so with the defaults you might see runs up to **97 days** old. Retention is counted from each run's **start time**.
</Step>

<Step id="billing" name="Its own bill" tag="TIP">
Storage isn't included in your plan. Storage transactions follow **Azure Storage pricing** and appear **separately** on your Azure bill, so a busy stateful logic app has a storage cost that grows with every run.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- Stateful workflows use **tables** (run state), **blobs** (run history: each action's inputs and outputs) and **queues** (scheduling).
- `AzureWebJobsStorage` is required.
- One account throttles above **20,000 requests per second**: spread work across workflows and storage accounts.
- Up to **32 storage accounts** with `Runtime.ScaleUnitsCount`, set up **before** you create the app.
- Run history is kept **90 days** by default (7–365), and storage is **billed separately**.
</Step>
