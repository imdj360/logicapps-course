<Step id="problem" name="No public endpoints" tag="PROBLEM">
The security team's rule: nothing on the public internet. The logic app must accept calls only from the company network, and reach databases that only exist there.

Standard handles this with two separate features, one for each direction.
</Step>

<Step id="directions" name="Two directions">
- **Inbound**: a **private endpoint** gives the logic app an address inside your virtual network.
- **Outbound**: **VNet integration** routes the app's calls into your virtual network.

They're independent: a private endpoint doesn't change outbound traffic, and VNet integration only affects outbound traffic. For the private endpoint you need a subnet **without delegations**.
</Step>

<Step id="inbound" name="Inbound: private endpoint">
Start with a trigger that accepts inbound requests, such as **Request**. Then on the logic app, under **Settings** > **Networking**, add a **private endpoint** in the inbound traffic section.

From outside the network, calls now get **403 Forbidden**, which is the expected result. To call the workflow you must be connected to the virtual network, for example from a VM in it.
</Step>

<Step id="breaks" name="What stops working" tag="PROBLEM">
Microsoft lists the side effects of a private inbound endpoint:

- **Managed webhook triggers and actions** don't work, such as Event Grid and Dataverse triggers: they run in the public cloud and can't call into your network.
- The **Office 365 Outlook** trigger only fires hourly.
- From outside the network, **monitoring view** can't show trigger and action inputs and outputs.
- **VS Code or Azure CLI** deployments work only from inside the network.
</Step>

<Step id="outbound" name="Outbound: VNet integration">
Under **Networking**, add **virtual network integration** in the outbound section and pick the subnet. You can't resize the subnet later: Microsoft recommends a **/26**, and the portal requires at least a **/27**.

By default, **all outbound traffic** goes through the virtual network. An HTTP action to a private IP that failed before now succeeds.
</Step>

<Step id="managed" name="Managed connectors still go out">
Managed connectors run in Azure, outside your network. If a firewall, NSG or route table controls outbound traffic, allow outbound connections to the **managed connector IP addresses** for your region, or they stop working.
</Step>

<Step id="storage" name="The storage account">
If the storage account behind the app sits behind private endpoints, open these ports from the integrated subnet: **443** to the storage account, **445** for the SMB file share, and **20000–30000** between the app's worker nodes.

Learn's deployment-slots page describes such a storage account with private endpoints for **Blob, File, Table and Queue**.
</Step>

<Step id="dns" name="Your own DNS" tag="TIP">
If your virtual network uses its own DNS server, add the app setting `WEBSITE_DNS_SERVER` with its IP address, and `WEBSITE_DNS_ALT_SERVER` for a secondary.
</Step>

<Step id="restrictions" name="Or restrict by IP">
If the endpoint stays public, **access restrictions** under Networking can allow or deny address ranges, a feature inherited from App Service. Separately, you can limit who can see **run history** inputs and outputs to specific IP ranges.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Private endpoint** for inbound, **VNet integration** for outbound; independent features.
- Expect **403** from outside; managed **webhook** triggers stop working.
- Use a **/26** subnet; allow outbound to **managed connector** IPs.
- Storage behind private endpoints: ports **443**, **445**, **20000–30000**.
- Custom DNS: `WEBSITE_DNS_SERVER`.
</Step>
