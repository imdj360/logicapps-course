<Step id="problem" name="Same workflow, three environments" tag="PROBLEM">
Your order-intake workflow calls a pricing API. The URL and key differ in dev, test and production, and you don't want to edit the workflow for each one.

Standard gives you two tools for this: **parameters** and **app settings**.
</Step>

<Step id="two" name="Two tools">
Microsoft says that in Standard you can work with environment variables both at runtime and at deployment by using **parameters and app settings**.

**App settings** are global configuration options for all workflows in the same logic app. **Parameters** let you design the workflow first and insert environment-specific values later.
</Step>

<Step id="params" name="parameters.json">
In VS Code, define parameters in a root-level `parameters.json`. Each key is a parameter name, and each value needs a **type** and a **value**.

The file must define every parameter you use anywhere in the project, including workflow definitions and connections. In a trigger or action, reference one with `@parameters('name')`. Parameters can hold large values and complex objects, such as an authentication object.
</Step>

<Step id="appsetting" name="@appsetting()">
Locally, app settings live in `local.settings.json` and act as local environment variables. You reference an app setting with `@appsetting('name')`.

Inside `parameters.json`, `@appsetting` is the **only valid expression type**. In `connections.json`, the only valid ones are `@parameters` and `@appsetting`. So a parameter can point at an app setting, and a workflow then uses `@parameters()`.
</Step>

<Step id="choose" name="Which one to use">
Learn's note: consider **parameters as the default** way to parameterize values. When you need to store secure keys or strings, reference app settings from your parameters.

Reasons: app settings have **size limits** and can't be referenced from certain areas, while parameters support large values and complex objects. In Learn's `connections.json` example, simple values use app settings because they're generated during deployment and are easy to populate in a pipeline.
</Step>

<Step id="env" name="Values per environment">
- **Parameters**: keep one `parameters.json` per environment and promote the matching file with your pipeline. Learn shows `az functionapp deploy ... --type static --target-path parameters.json`. Replacing the file isn't available in the portal or designer.
- **App settings**: set in the portal under **Settings > Environment variables > App settings**, with `az logicapp config appsettings set`, or from your pipeline with the `appSettings` parameter of the Azure Function App Deploy task.
</Step>

<Step id="secrets" name="Where secrets go">
Learn's guidance: secure data types such as `securestring` and `secureobject` **aren't supported** in Standard parameters. Authenticate with a **managed identity** when possible.

If that's not possible, secure connection strings by other means, such as **Azure Key Vault**, which you can use with app settings. Don't put a secret in plain text in `parameters.json` (ours, following from the above).
</Step>

<Step id="keyvault" name="Key Vault references">
An app setting can hold a reference such as `@Microsoft.KeyVault(SecretUri=https://myvault.vault.azure.net/secrets/mysecret)`. The app's **system-assigned identity** is used by default, and it needs read access to secrets (for example the **Key Vault Secrets User** role).

Without a version in the reference, the app picks up a newer secret version **within 24 hours**. Store only real secrets there: the designer **can't dereference** an app setting that points to Key Vault, so keep nonsecret values, such as URLs, directly in app settings.
</Step>

<Step id="slots" name="Per-slot values and the designer" tag="TIP">
The Azure Functions slots article describes marking a setting as a **Deployment slot setting**. App Service guidance on Key Vault references says most such settings should be marked as slot settings, since you should have separate vaults per environment.

If you parameterize `connections.json`, the designer becomes **restricted**, locally and in the portal. Learn suggests developing with a nonparameterized file and replacing it in your deployment pipeline.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **App settings** are app-wide; **parameters** live in `parameters.json` and take large or complex values.
- Use `@parameters()` in workflows and connections; use `@appsetting()` in parameters and connections.
- Keep a **parameters file per environment**; set app settings per environment.
- No secure types in Standard; prefer **managed identity**, otherwise **Key Vault** through app settings.
- Keep nonsecret values out of Key Vault references the designer must resolve.
</Step>
