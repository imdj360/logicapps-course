<Step id="problem" name="Same workflow, three environments" tag="PROBLEM">
Your order-intake workflow calls a pricing API. Dev, test and production each have their own **URL** and **key**.

You don't want to edit the workflow for each environment, and the key must never sit in the workflow at all.
</Step>

<Step id="two" name="The idea">
**The workflow never holds the values. It asks for them by name.**

Follow one value down the chain:

1. The workflow uses `@parameters('pricingKey')`.
2. `parameters.json` says where `pricingKey` comes from: an app setting.
3. The app setting `PricingKey` points at a secret in **Key Vault**.

The URL is not a secret, so it stops at step 2.
</Step>

<Step id="params" name="parameters.json">
One file at the root of the project lists every parameter, each with a **type** and a **value**:

```json
{
  "pricingUrl": { "type": "string", "value": "https://pricing-dev.contoso.com" },
  "pricingKey": { "type": "string", "value": "@appsetting('PricingKey')" }
}
```

In a trigger or action you write `@parameters('pricingUrl')`. Inside `parameters.json`, `@appsetting(...)` is the **only expression** allowed.
</Step>

<Step id="appsetting" name="App settings">
App settings are **app-wide** configuration for all workflows in the logic app:

- **Locally**: in `local.settings.json`.
- **In Azure**: **Settings** > **Environment variables** > **App settings**.

For the secret, the app setting holds a Key Vault reference instead of the key:

```text
PricingKey = @Microsoft.KeyVault(SecretUri=https://myvault.vault.azure.net/secrets/pricing-key)
```

The app reads it with its **system-assigned identity**, which needs read access to the secret: the **Key Vault Secrets User** role if the vault uses Azure RBAC, or the **Get** secrets permission with access policies.
</Step>

<Step id="choose" name="Which one when?">
- **Parameters**: the default. They hold large values and complex objects.
- **App settings**: when a value is a **secret**, or your pipeline sets it during deployment. Reference them from parameters.
- **Key Vault**: for the secret itself, through an app setting. Standard parameters don't support `securestring` or `secureobject`, and Microsoft prefers a **managed identity** when the target supports it.
</Step>

<Step id="env" name="Values per environment">
- **Parameters**: keep one `parameters.json` per environment, and let your pipeline deploy the matching file, for example `az functionapp deploy ... --type static --target-path parameters.json`.
- **App settings**: set them per environment in the portal, with `az logicapp config appsettings set`, or from your pipeline.

The workflow itself is the same file everywhere.
</Step>

<Step id="watch" name="Watch out" tag="TIP">
- The designer **can't resolve** an app setting that points at Key Vault, so keep only real secrets there. Values like the URL stay plain.
- Parameterizing `connections.json` restricts the designer. Develop with a plain file and swap in the parameterized one in your pipeline.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- The workflow asks with `@parameters('name')`.
- `parameters.json` holds plain values, or `@appsetting('Name')` for secrets.
- The app setting holds a **Key Vault reference** for the secret.
- One `parameters.json` and one set of app settings per environment; the workflow never changes.
</Step>
