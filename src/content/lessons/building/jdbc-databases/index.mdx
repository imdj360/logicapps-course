<Step id="problem" name="A database with no connector" tag="PROBLEM">
Your stock levels live in a MySQL database, or in AWS Aurora. There's no dedicated Logic Apps connector for it, and you don't want to build an API in front of it just to read a table.

If the database has a **JDBC driver**, a Standard logic app can talk to it directly.
</Step>

<Step id="what" name="The JDBC built-in connector">
**JDBC** is a **built-in** connector, available **only in Standard**. You bring the JDBC driver, a set of JAR libraries, for any JDBC-supported relational database, and the connector uses it. Microsoft names SQL Server, AWS Aurora and MySQL as examples.

Like other built-in connectors, it doesn't need the **on-premises data gateway**.
</Step>

<Step id="driver" name="Bring your own driver">
The driver JARs are a **Client or SDK Assembly (Java)** artifact. Add them in one of three ways:

- **Portal**: on the logic app, under **Artifacts** > **Assemblies**, add them with that assembly type.
- **VS Code**: put them in your project's `lib/builtinOperationSdks/JAR` folder.
- **Kudu**: upload them to `site/wwwroot/lib/builtinOperationSdks/JAR/`.
</Step>

<Step id="package" name="Package the JAR with your project">
In a VS Code project, the driver travels with your code. The `lib` folder sits at the project root, next to your workflow folders:

```text
MyLogicApp/
├── lib/
│   └── builtinOperationSdks/
│       └── JAR/
│           └── ojdbc11.jar
├── StockSync/
│   └── workflow.json
├── connections.json
└── host.json
```

To deploy, zip the project **contents** so the workflow folders, `lib` and `host.json` sit at the root of the zip, with no extra wrapper folder, then deploy the zip, for example:

```bash
az logicapp deployment source config-zip --name MyLogicApp \
  --resource-group MyResourceGroup --src MyBuildArtifact.zip
```

Put **every** JAR the driver needs in the `JAR` folder.
</Step>

<Step id="connect" name="The connection">
A JDBC connection takes three values: the database **URL**, a **user identifier** and a **password**.

Learn doesn't give URL examples. The JDBC URL format, typically starting with `jdbc:`, comes from **your driver's documentation**. Our advice: store the password as a secret in app settings, not in the workflow.
</Step>

<Step id="oracle" name="Example: Oracle over JDBC">
Oracle works the same way. Learn's JDBC page doesn't use Oracle as its example, but "any JDBC-supported relational database" includes it.

- **Driver**: Oracle's JDBC driver JAR (the `ojdbc` family), downloaded from Oracle and added like any other driver JAR.
- **URL**: Oracle's thin-driver format, for example `jdbc:oracle:thin:@//db-host:1521/ORDERS`.
- **User and password**: a database account with only the rights the workflow needs.

The driver name and URL format come from Oracle's JDBC documentation, not from Learn; check the driver version against Oracle's compatibility notes.
</Step>

<Step id="actions" name="Three actions">
The connector has **actions only**, no triggers:

- **Execute query**: runs a raw query, with optional **query parameters** to inject.
- **Get tables**: lists the tables in the database.
- **Get schema**: returns the schema of a table.

So a workflow starts with another trigger, such as a schedule or a queue message, and queries the database from there.
</Step>

<Step id="params" name="Use query parameters" tag="TIP">
Don't build SQL by concatenating values from the trigger into the query text. Pass them through the action's **query parameters** input instead. That's our advice, the same as for any database code: it keeps data from being read as SQL.
</Step>

<Step id="alternatives" name="JDBC or a dedicated connector?">
JDBC is the generic option. Two databases also have their own built-in connectors in Standard:

- **SQL Server**: actions to insert, update and run stored procedures, **triggers** on inserted, updated or deleted rows (with change tracking), and managed identity authentication.
- **Oracle Database**: a built-in connector, in **public preview**, for Oracle 11 and later. No data gateway, and Learn lists no driver-upload step; it connects with `host:port/service-name`. It has actions only, and a default query timeout of 30 seconds.

So for Oracle you have two built-in routes. The **Oracle Database** connector gives you ready-made operations such as Get rows, Insert row and stored procedures, but it's in preview. **JDBC** gives you raw queries through a driver you control. For SQL Server, the dedicated connector adds triggers and managed identity, which JDBC doesn't offer.
</Step>

<Step id="network" name="Reaching the database">
Built-in connectors run inside your logic app, so the database must be **reachable from the runtime**. For Oracle, Microsoft describes using **VNet integration** for private endpoints, or the **hybrid** model for databases on your own infrastructure. Learn's JDBC page doesn't cover networking; our reasoning is that any built-in connector still needs a network path from the runtime.
</Step>

<Step id="gaps" name="What Learn doesn't cover" tag="TIP">
The JDBC reference is short. Learn doesn't state a required Java version, URL examples, which SQL statements are supported, or whether the connector is preview or generally available. Test with your driver and database before you rely on it.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **JDBC** is a Standard-only built-in connector: bring your database's JDBC driver.
- Add the JARs as **Client or SDK Assembly (Java)**, or package them in `lib/builtinOperationSdks/JAR` and zip-deploy the project.
- Connect with a **URL**, **user** and **password**; actions are **Execute query**, **Get tables** and **Get schema**.
- **Oracle** works over JDBC too, with Oracle's driver and `jdbc:oracle:thin:` URL; compare it with the Oracle Database built-in (preview).
- Pass values as **query parameters**, and test what Learn doesn't document.
</Step>
