<Step id="problem" name="The whole picture" tag="PROBLEM">
The shop sends orders. The ERP must receive each one **exactly once in effect**, even when it's slow or down for maintenance. The shop must get an answer in seconds.

No single feature does all that. This capstone combines the patterns from earlier modules into one design. The design is ours; each building block cites Microsoft.
</Step>

<Step id="front" name="A fast front door">
A workflow with a **Request** trigger accepts the order, checks the basics, and puts it on a **Service Bus queue**. It answers right away: a Response with **202 Accepted**, or the asynchronous response setting.

Microsoft's integration architecture points out the benefit: a queue lets you **queue messages when a back-end system isn't available**.
</Step>

<Step id="queue" name="The queue decouples">
The queue absorbs bursts and outages. Microsoft's reference architecture for message brokers and events lists the **queue-based load leveling** pattern, to handle bursts in workloads, as one advantage of putting Service Bus between systems.

Give each message a **MessageId** from the order number. With **duplicate detection** enabled on the queue (Standard or Premium tier), Service Bus drops resends with the same MessageId within its time window.
</Step>

<Step id="process" name="Process with peek-lock">
A second workflow uses the **built-in** Service Bus trigger in **peek-lock** mode. Microsoft's architecture guidance: with peek-lock, the workflow can **validate each message before completing or abandoning it**, which prevents accidental message loss.

The workflow is **stateful**, so every run has history and can be resubmitted.
</Step>

<Step id="transform" name="Transform and write">
Reshape the order for the ERP with a **Liquid** template (JSON) or an **XSLT** map (XML). Then call the ERP, with a **retry policy** for temporary failures and a **timeout** that matches how long the business can wait.

Make the write **idempotent**: upsert by order number, or check before creating, so a retry or resubmit can't create a second order.
</Step>

<Step id="failures" name="When it fails">
Wrap the processing in a **Try** scope with a **Catch** scope that runs on failure or timeout. Catch alerts the team with the details from `result('Try')`, then ends with **Terminate (Failed)** so the run shows as Failed.

Messages that can't be processed go to the **dead-letter queue**, where a small workflow can alert and help repair them.
</Step>

<Step id="observe" name="See it running">
Use the order number as the trigger's **custom tracking ID** (shown as ClientTrackingId in the logs), so you can find any order's runs. Alert on **Workflow Runs Failure Rate** for the processing workflow, and on **Workflow Job Execution Delay** if orders start to wait.
</Step>

<Step id="scale" name="Room to grow" tag="TIP">
If volume grows, the queue keeps the shop fast while the processing side scales. Watch the storage account and connector limits, and split heavy work across workflows or logic apps, as in the throttling and storage lessons.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Front door**: Request trigger, quick checks, queue, answer **202**.
- **Queue**: load leveling, duplicate detection on a business MessageId.
- **Back end**: built-in Service Bus trigger, **peek-lock**, stateful.
- Transform, call the ERP with **retries and timeouts**, write **idempotently**.
- **Try/Catch**, dead-letter handling, tracking IDs and alerts.
</Step>
