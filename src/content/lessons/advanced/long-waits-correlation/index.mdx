<Step id="problem" name="Three days for a yes" tag="PROBLEM">
Large orders need a **credit check** from the finance team. They take **three days** to answer.

Meanwhile the order workflow must wait, without polling, and continue exactly where it stopped. And with many orders waiting, each answer must reach the right order.
</Step>

<Step id="pattern" name="The idea">
**Pause the run, give the other side a way to wake it up.**

Like leaving your number at a busy restaurant: you don't stand at the door, they call you when your table is ready.
</Step>

<Step id="sequence" name="How it flows">
1. The order workflow **asks finance** and hands over a **callback URL**.
2. The run **pauses**. Nothing is polled.
3. Finance **posts the answer** to the callback URL.
4. The run **wakes up** and continues with the answer.
</Step>

<Step id="build" name="Build it in Logic Apps">
Our build in Standard, with a **stateful** workflow:

1. Any trigger starts the order workflow.
2. The **HTTP Webhook** action calls finance's **subscribe** endpoint and sends the callback URL, taken from the `listCallbackUrl()` function in **Subscribe Body**.
3. The run pauses until finance sends an HTTP POST to that URL.
4. The action then unsubscribes, and the workflow continues.

The Office 365 Outlook action **Send approval email** follows the same webhook pattern, for human decisions by email.
</Step>

<Step id="limits" name="How long can it wait?">
- **Stateful** run: **90 days** by default. Change it with `Runtime.Backend.FlowRunTimeout` (minimum 7 days).
- **Stateless** run: **5 minutes** by default.
- **HTTP Webhook** action in Standard: up to **30 days** stateful, **5 minutes** stateless.

Set a shorter wait with `limit.timeout` on the action. Long waits belong in **stateful** workflows.
</Step>

<Step id="callback" name="Guard the callback URL" tag="PROBLEM">
The callback URL stays valid for the run duration. It stops working if you:
- **cancel** the workflow,
- **delete or disable** the workflow or logic app,
- **rotate** the workflow's access keys, or
- the workflow **times out**.

Treat it like a password (ours): send it only to the service that needs it.
</Step>

<Step id="correlation" name="Which answer is which?">
Give every order a **tracking ID**, for example the order number.

- Most triggers have a **Custom Tracking Id** property.
- For a Request, HTTP or webhook-based trigger, you can also pass an `x-ms-client-tracking-id` header.

It shows up as **ClientTrackingId** in Log Analytics. The HTTP Webhook action also sends `x-ms-client-tracking-id` and `x-ms-workflow-operation-name`, so finance can tell which subscriber is calling.
</Step>

<Step id="split" name="Or split the wait (option)" tag="TIP">
For very long or uncertain waits, don't pause at all (ours).

1. Workflow one sends the request, **saves the order's state** under its order ID, and ends.
2. The answer arrives as an HTTP call or a queue message with the same ID.
3. **Workflow two** loads the state and continues.

No run sits waiting for days, and a lost callback leaves nothing hanging.
</Step>

<Step id="timeout" name="Plan for silence" tag="TIP">
Whatever you pick, decide what happens when **nobody answers**: remind, escalate or cancel. In the pausing design, a run after set to **Has timed out** can catch it (ours).
</Step>

<Step id="when" name="When to use it">
**Pause with a webhook** when the answer comes within days and the service can call you back.

**Split in two** (ours) when the wait is very long, the answer may never come, or you want no run left open.

**Skip both** when the answer arrives in seconds: a normal call is enough.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **HTTP Webhook** pauses a run until a callback.
- Stateful runs last **90 days** by default, webhooks **30 days** in Standard stateful. Stateless: **5 minutes**.
- The callback URL dies with a cancel, a disable or delete, a key rotation or a timeout.
- Match answers to orders with a **tracking ID**.
- For very long waits, split in two. Always plan for no answer.
</Step>
