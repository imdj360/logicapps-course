<Step id="problem" name="A quote that takes minutes" tag="PROBLEM">
An order workflow needs a **price quote** from the pricing engine. The engine takes **3 to 10 minutes**.

An HTTP call won't wait that long: an outbound request in Standard times out after **225 seconds** by default.
</Step>

<Step id="pattern" name="The idea">
**Send the question as a message, and read the answer from another queue.**

Like posting a letter with a return address on it (ours): you don't stand at the door waiting. The reply finds its way back.
</Step>

<Step id="two" name="Not the same as HTTP 202">
Two patterns, same goal:

- **HTTP request-reply**: the server answers **202 Accepted** with a status URL, and you poll. Microsoft's *Asynchronous Request-Reply* pattern, covered in the async polling lesson.
- **Messaging request-reply**: the request goes on one queue, the reply comes back on another. This lesson.
</Step>

<Step id="sequence" name="How it flows">
1. The order workflow **sends the request** with a **MessageId** and a **ReplyTo**: the queue for the answer.
2. The pricing engine calculates the quote.
3. It **copies the MessageId** into the reply's **CorrelationId**, and sends the reply to the ReplyTo queue.
4. The order workflow reads the reply and **matches CorrelationId** to its request.
</Step>

<Step id="sessions" name="Many requesters, one reply queue">
Many orders wait at once on one reply queue. Each must get only its own reply. Use **sessions**. Microsoft calls this *multiplexed* request-reply:

1. The requester sets **ReplyToSessionId** to a unique ID, such as a GUID.
2. The responder copies it into the reply's **SessionId**.
3. The requester reads only that session.

Sessions need Service Bus **Standard or Premium**.
</Step>

<Step id="build" name="Build it in Logic Apps">
Our build in Standard:

**Requester workflow**
1. **Send message** (Service Bus): set **Message Id**, **Reply To**, **Reply To Session Id** and **Correlation Id**. The managed connector documents these fields (message limit **1 MB**). The built-in one shows them under **Advanced parameters** in the designer (ours: its reference lists only the queue name and the message).
2. **Get messages from a queue session** (built-in), with **Session Id** set to your GUID.

**Responder workflow** (ours)
1. Trigger: **When messages are available in a queue (peek-lock)**.
2. **Send message**, with **Session Id** set to the request's Reply To Session Id and **Correlation Id** set to its Message Id.
</Step>

<Step id="wait" name="Wait, with a deadline">
Our design for waiting: put **Get messages from a queue session** inside an **Until** loop, with a **Delay** between tries.

In a stateful workflow, Until stops after **60 iterations** or **PT1H** by default, whichever comes first (stateless: **PT5M**). Set limits that match your longest expected quote (ours).
</Step>

<Step id="multicast" name="Several answers (option)" tag="TIP">
Send the request to a **topic** instead, and every subscriber may reply. Microsoft calls this **multicast** request-reply, used for discovery or roll-call scenarios.

The scatter-gather lesson builds on this.
</Step>

<Step id="watch" name="When no reply comes" tag="PROBLEM">
Plan for the quote that never arrives, or arrives late (ours):

- After the Until loop ends, check whether a reply came. If not, **alert or compensate**.
- Decide what happens to a reply that arrives **after** you gave up.
- Keep requests **idempotent**: a retried request may produce two replies.
</Step>

<Step id="when" name="When to use it">
**Use it** when the answer takes longer than an HTTP call can wait, or when the responder may be busy or offline.

**Skip it** when the answer comes back in seconds: a plain HTTP call is simpler.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- Send the **request** as a message. Read the **reply** from a queue.
- **ReplyTo** says where to answer. **CorrelationId** links reply to request.
- **ReplyToSessionId** plus sessions let many requesters share one reply queue.
- Standard: **Send message** sets the properties (check Advanced parameters). Built-in **Get messages from a queue session** reads the reply.
- Always design for a reply that never comes.
</Step>
