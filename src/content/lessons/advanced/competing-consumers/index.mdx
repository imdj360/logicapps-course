<Step id="problem" name="One worker is too slow" tag="PROBLEM">
Every night, **50,000 invoices** land on a queue. One workflow handles one invoice at a time, so it would finish around noon.

And a few dozen of them are **urgent credit notes** that shouldn't wait in line.
</Step>

<Step id="pattern" name="The idea">
**Several workers read the same queue. Each message goes to only one of them.**

Like checkout lanes at a supermarket: one line of shoppers, many tills, and each shopper is served once. Microsoft calls this the **Competing Consumers** pattern.
</Step>

<Step id="sequence" name="How it flows">
1. Invoices wait in **one queue**.
2. Each worker **takes the next message**. The queue hides it from the other workers.
3. When the worker **finishes**, the message is removed.
4. If the worker **fails**, the message goes back and another worker tries.
</Step>

<Step id="build" name="Build it in Logic Apps">
Our build in Standard, with built-in Service Bus actions:

1. Trigger: **When messages are available in a queue (peek-lock)**.
2. Process the invoice.
3. On success: **Complete the message in a queue**.
4. On failure: **Abandon the message in a queue**, so another worker can try.

Each workflow instance is one consumer.
</Step>

<Step id="scale" name="Add more workers">
Two ways to get more workers:

- **Trigger concurrency**: off by default, which means unlimited runs. Turn it on and pick **1 to 100** runs in parallel (Standard default when on: 100). It **can't be turned off again**.
- **More instances** of your Standard app. We expect each instance to compete for the queue too (ours; the Microsoft Learn docs don't say).
</Step>

<Step id="order" name="Order and duplicates" tag="PROBLEM">
Many workers means two surprises:

- **Order isn't guaranteed.** Invoice 7 may finish before invoice 3. If order matters, Service Bus **sessions** can give first-in-first-out.
- A queue delivers **at least once**, so one invoice can arrive twice. Make processing **idempotent**: doing it twice gives the same result as once.
</Step>

<Step id="poison" name="Poison messages" tag="PROBLEM">
One malformed invoice can fail on every worker that tries it.

Service Bus counts deliveries. When the count passes **MaxDeliveryCount**, it moves the message to the **dead-letter queue**. Or end the run yourself with **Dead-letter the message in a queue**.

Then a separate workflow (ours) can alert someone and repair it.
</Step>

<Step id="priority" name="Give urgent work its own lane">
Microsoft's **Priority Queue** example uses a Service Bus **topic**:

1. The sender sets a **Priority** property on each message.
2. **SQL filters** route urgent and normal messages to separate **subscriptions**.
3. Each subscription has its own workers, more of them for urgent.

In Logic Apps (ours): one workflow per subscription, using **When messages are available in a topic subscription (peek-lock)**.
</Step>

<Step id="starvation" name="Don't starve the rest" tag="TIP">
If one pool favours urgent work, normal messages can be **delayed for a long time, or never processed**.

Two fixes from Microsoft: **raise the priority of old messages** over time, or give each priority its own pool of workers.
</Step>

<Step id="when" name="When to use it">
**Use it** when work items are independent, can run in the background, and come in variable volumes.

**Skip it** when tasks must run in strict order or depend heavily on each other.

Priority lanes fit different service levels, such as premium and standard customers.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Many workers, one queue**, each message to one worker.
- Build: peek-lock trigger, then **Complete** or **Abandon** the message.
- Scale with trigger concurrency (1 to 100) or more instances.
- No ordering, at-least-once delivery: be **idempotent**. Poison messages go to the dead-letter queue.
- Urgent lane: topic, **Priority** property, SQL filters.
</Step>
