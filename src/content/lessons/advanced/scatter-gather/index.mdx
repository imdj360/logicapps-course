<Step id="problem" name="Best price, fast" tag="PROBLEM">
For each large order, purchasing wants quotes from three suppliers and picks the cheapest that can deliver. Asking one after another takes too long; some suppliers answer slowly, and one may not answer at all.

**Scatter-gather** sends the request to all of them at once, then **gathers** the replies and combines them.
</Step>

<Step id="honest" name="What Learn covers">
Scatter-gather is a classic enterprise integration pattern, but the Azure Architecture Center has **no pattern page** for it; there, the name appears only as another name for concurrent orchestration of AI agents. Learn's BizTalk Server ESB Toolkit docs describe a scatter-gather pattern, but for a different product.

So this lesson builds it from pieces Learn **does** document: parallel branches, Service Bus topics, multicast request-reply and timeouts. The combination is our design.
</Step>

<Step id="branches" name="Scatter with branches">
When the suppliers have **APIs you call directly**, use **parallel branches**: one branch per supplier, each with an HTTP or connector action.

A **join** action after the branches waits for all branches at the same level to finish. Set its **run after** to include *Has failed* and *Has timed out*, so one failing supplier doesn't stop the gather.
</Step>

<Step id="deadline" name="Give each call a deadline">
A slow supplier shouldn't hold up the rest. Set the HTTP action's **Timeout** under Settings > Request options; Learn says the action then fails if the server doesn't respond in time (by default, after 225 seconds in Standard). Connector actions may not offer the setting. Then the join compares whatever came back.
</Step>

<Step id="topics" name="Scatter with a topic">
When suppliers are **decoupled** and answer later, publish one request to a Service Bus **topic**, with a subscription per supplier. Each supplier replies to a reply queue, with a **CorrelationId** that matches the request.

Service Bus calls this **multicast** request-reply: one request, potentially several replies.
</Step>

<Step id="gather" name="Gather the replies">
To gather, our design: an **Until** loop reads replies for this request, by correlation or session ID, and adds them to an array variable. It stops when all suppliers have answered **or** the deadline passes, then picks the best quote.

Keep the loop's own timeout in mind: one hour by default in a stateful workflow.
</Step>

<Step id="choose" name="Branches or topic?" tag="TIP">
Our rule of thumb: **branches** when the suppliers are known APIs that answer within seconds; a **topic** when suppliers come and go, or answer minutes later. Topics make adding a supplier a configuration change, not a workflow change.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Scatter-gather**: ask many at once, combine the answers.
- Learn has no pattern page for it; build it from documented pieces.
- **Branches** plus a **join** for direct API calls; give each call a timeout.
- A **topic** plus a reply queue and **CorrelationId** for decoupled suppliers.
- Gather with a deadline, and decide what "good enough" means.
</Step>
