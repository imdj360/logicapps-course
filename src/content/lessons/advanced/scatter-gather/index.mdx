<Step id="problem" name="Three quotes, fast" tag="PROBLEM">
For every big order, purchasing wants a price from **three suppliers** and takes the cheapest.

Asking them one after another is slow. And if Supplier C never answers, the whole order waits.
</Step>

<Step id="idea" name="The idea">
**Ask everyone at once. Collect the answers. Choose.**

Like asking three plumbers for a quote on the same day, then calling the cheapest one back. This is **scatter-gather**: scatter the request, gather the replies. It's a classic integration pattern with no Architecture Center page, so we build it from documented pieces (ours).
</Step>

<Step id="flow" name="How it flows">
1. An order arrives and needs quotes.
2. **Scatter**: the same request goes to Suppliers A, B and C at once.
3. **Gather**: replies come back, each at its own speed.
4. A deadline passes. We use the replies that arrived and **pick the cheapest**.
</Step>

<Step id="branches" name="Build it with branches">
Use this when you call the suppliers' **APIs directly** and they answer in seconds.

1. Trigger: whatever receives the order (ours).
2. Add **parallel branches**, one per supplier, each with an **HTTP** action.
3. Under all the branches, add a **join** action. It runs only after **all** branches finish.
4. Pick the cheapest of the replies that came back (ours).
</Step>

<Step id="deadline" name="Don't wait forever" tag="PROBLEM">
Supplier C is down. Without care, one failed branch stops the join.

- On the join, open its **run after** settings and also select **Has failed** and **Has timed out**. The join then runs anyway.
- On each **HTTP** action, set a shorter timeout under **Settings > Request options > Timeout**. In Standard an outbound request waits up to **225 seconds**, which is the default and also the maximum. You can only lower it.
</Step>

<Step id="topic" name="Build it with a topic (option)">
Use this when suppliers answer **minutes later**, or come and go.

**Scatter workflow**
1. **Send message** (Service Bus) to a **topic**, with a message ID.
2. Each supplier has its own **subscription** and replies to a **reply queue**, copying the request ID into the reply's **CorrelationId**.

One request, several replies: Service Bus calls this **multicast request/reply**. Adding a supplier is a new subscription, not a workflow change (ours).
</Step>

<Step id="gather" name="Gather the replies">
Our design for the topic version, in a second workflow or a later stage:

1. An **Until** loop runs **Get messages from a queue** on the reply queue.
2. Keep replies whose CorrelationId matches this order, in an array variable.
3. Stop when all three have answered **or** the deadline passes.
4. Pick the cheapest quote.

An **Until** loop stops after **60 iterations** or **PT1H** (one hour) by default in a stateful workflow. Set your own limits.
</Step>

<Step id="watch" name="Decide what good enough means" tag="TIP">
Only two of three answered? Decide **before** go-live (ours): is two enough, or must you wait for all three?

Also log which supplier was late, so you can see who is slow.
</Step>

<Step id="when" name="When to use it">
**Use it** when you need the best of several answers, and the answers are independent of each other.

**Skip it** when one supplier is enough, or when each call depends on the result of the one before.

**Branches** for known, fast APIs. **A topic** for slow or changing suppliers (ours).
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Scatter-gather**: ask many at once, combine the answers.
- Direct APIs: parallel branches, then a join with run after set to include Has failed and Has timed out.
- Slow suppliers: Send message to a topic, replies matched by CorrelationId.
- Set a deadline, so one slow supplier can't block the order.
- Decide up front what a partial answer is worth.
</Step>
