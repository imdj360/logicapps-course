<Step id="problem" name="Out of order" tag="PROBLEM">
Order updates arrive in sequence: created, changed, cancelled. With several workflow runs reading the same queue in parallel, "cancelled" can be processed before "changed", and the order comes back to life.

A single reader keeps the order but can't scale. Microsoft's **Sequential Convoy** pattern gives you both.
</Step>

<Step id="pattern" name="The pattern">
Group related messages by a **category key**, such as the order ID. Process each group **one message at a time**, in order, while **different groups run in parallel**.

Microsoft notes that on Azure, **Service Bus message sessions** are a built-in implementation of this pattern.
</Step>

<Step id="sessions" name="Sessions">
The sender sets each message's **SessionId** to the category key. In a session-enabled queue:

- A receiver that accepts a session gets an **exclusive lock** on all its messages, including ones that arrive later.
- Only **one receiver** holds a session at a time, and receives its messages **in order**.

Sessions need the **Standard or Premium** tier, and once sessions are enabled on a queue, clients can't send or receive regular messages on it.
</Step>

<Step id="logicapps" name="In Logic Apps">
Learn's Logic Apps guide for this pattern offers a **Standard** template: *Azure Service Bus: Process related messages from a session-enabled queue for the same workflow instance - Sequential convoy pattern*. In Consumption, you build the workflow yourself.

The workflow starts with the **peek-lock** trigger, initializes the session from the first message, and processes **all messages from that session in the same run**. The next run handles the next session.
</Step>

<Step id="locks" name="Keep the lock alive">
A session can take a while to process. In Learn's design, a **parallel branch** runs an **Until** loop that calls **Renew lock** with a delay shorter than the lock timeout; the minimum lock duration is **30 seconds**.

If processing fails, **Abandon** unlocks the message and puts it back for another attempt.
</Step>

<Step id="poison" name="One bad message blocks the session" tag="PROBLEM">
A message that keeps failing blocks **every message after it** in that session. Microsoft's advice: move it to the **dead-letter queue** after a retry threshold. In Service Bus, that happens automatically once **MaxDeliveryCount** (default **10**) is exceeded.

Careful: if you later move a dead-lettered message back, its original order within the session is lost.
</Step>

<Step id="key" name="Choose the key" tag="TIP">
The session key is the unit of parallelism. Too coarse, such as (our example) one key per country, and there's little parallelism; each session's throughput is limited by how long one message takes.

Microsoft says the pattern doesn't fit extremely high throughput, millions of messages a minute (reconsider whether strict FIFO is needed), or work where order doesn't matter (use competing consumers).
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Sequential convoy**: in order within a group, parallel across groups.
- **Sessions** implement it: SessionId = category key, one receiver per session.
- Standard has a **template** that processes a whole session per run, with peek-lock.
- **Renew the lock** for long sessions; dead-letter **poison** messages.
- Pick a session key that gives real parallelism.
</Step>
