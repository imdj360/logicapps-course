<Step id="problem" name="Out of order" tag="PROBLEM">
Updates for order 4711 arrive as **created**, **changed**, **cancelled**.

Several workflow runs read the same queue in parallel. One run can handle **cancelled** before another handles **changed**, and the cancelled order comes back to life.

One reader keeps the order, but can't scale.
</Step>

<Step id="pattern" name="The idea">
**Keep each order's messages in order. Let different orders run at the same time.**

Like a post office with one clerk per customer file (ours): all papers for one file go to the same clerk, in order. Different files go to different clerks at once. Microsoft calls this **Sequential Convoy**.
</Step>

<Step id="sessions" name="Sessions do the work">
The category key is the order ID. In Service Bus, a **session** is a group of messages with the same **SessionId**.

- A receiver that accepts a session gets an **exclusive lock** on its messages, including ones that arrive later.
- Only **one receiver** holds a session at a time.

Sessions need **Standard or Premium**. Once sessions are on, a queue accepts only session messages.
</Step>

<Step id="sequence" name="How it flows">
1. The order system sends each update with **SessionId = order ID**.
2. A workflow run accepts **one session**, say order 4711.
3. It processes that order's messages **one by one, in order**.
4. Another run takes order 4712 **at the same time**.
</Step>

<Step id="build" name="Build it in Logic Apps">
In Standard, start from the template **Azure Service Bus: Process related messages from a session-enabled queue for the same workflow instance - Sequential convoy pattern**.

It gives you:
1. Trigger: **When messages are available in a queue (peek-lock)**.
2. **Initialize variable**, a flag named **processCompleted**.
3. A **Scope** where your business logic goes.
4. **Complete the message in a queue** on success, **Abandon the message in a queue** on failure.

One run handles **all messages of one session**.
</Step>

<Step id="locks" name="Keep the lock alive">
Long work can outlast the message lock. The template runs a **parallel branch** with an **Until** loop:

1. **Renew lock on a message in a queue**.
2. **Delay** (named Wait for Process to Complete), shorter than the lock timeout.

The loop stops when **processCompleted** is true. The minimum lock duration is **30 seconds**.
</Step>

<Step id="poison" name="One bad message blocks the order" tag="PROBLEM">
A message that keeps failing blocks **every message after it** in that session.

Microsoft's advice: move it to the **dead-letter queue** after a retry threshold. In Service Bus, that happens automatically once **MaxDeliveryCount** (default **10**) is exceeded.

If you later move it back, its original place in the session is lost.
</Step>

<Step id="key" name="Choose the key" tag="TIP">
The session key is your unit of parallelism.

- **Too coarse** (one key for a whole customer, say): little parallelism.
- **Too fine**: no useful ordering.

Each session is as fast as one message takes to process. Producers must set the key correctly on every message.
</Step>

<Step id="when" name="When to use it">
**Use it** when messages must be processed in order, and you can split them into groups, like orders.

**Skip it** when order doesn't matter (use competing consumers), or at extreme volume, millions of messages a minute, where strict order limits scale.
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- **Sequential convoy**: in order within a group, parallel across groups.
- Sessions do it: **SessionId = order ID**, one receiver per session.
- Standard has a **template**: one run handles one whole session.
- **Renew the lock** for long work. **Dead-letter** poison messages.
- Pick a key that gives real parallelism.
</Step>
