<Step id="problem" name="No rollback" tag="PROBLEM">
An order passes through three systems: **reserve stock**, **charge the card**, **book the courier**.

The courier booking fails. Stock is reserved and the card is charged, and each system has already saved its change. There's nothing to roll back across them.
</Step>

<Step id="idea" name="The idea">
**Can't undo it? Do the opposite.**

Like a shop till: if the card is declined after the items are scanned, the cashier voids the items one by one. A **saga** is a chain of small steps, each saved in its own service. If one fails, **compensating transactions** undo the steps already done: release the stock, refund the card.
</Step>

<Step id="kinds" name="Three kinds of step">
- **Compensable**: can be undone by an opposite step. Reserve stock, charge the card.
- **Pivot**: the point of no return. Booking the courier.
- **Retryable**: steps after the pivot. They must be safe to repeat (**idempotent**) and are retried if they fail temporarily.

Put risky steps **before** the pivot (ours).
</Step>

<Step id="flow" name="How it flows">
1. **Reserve stock**. Done.
2. **Charge the card**. Done.
3. **Book the courier**. Fails.
4. **Compensate**: refund the card, then release the stock.
5. Tell the customer the order didn't go through.
</Step>

<Step id="build" name="Build it in Logic Apps">
Our design in a Standard workflow:

1. Put the three steps in order inside a **Scope** named Try (ours).
2. After each step, record what's done (ours).
3. Add a second **Scope**, Catch (ours). In its **run after** settings select **Has failed** and **Has timed out** on the Try scope.
4. In Catch, run a compensation for each recorded step: refund, then release.

A scope gets its own status, such as Succeeded, Failed or TimedOut, so Catch can react to it.
</Step>

<Step id="orchestration" name="Who is in charge? (option)">
- **Orchestration**: one central **orchestrator** tells each service what to do. Good for complex flows. The orchestrator is a point of failure, because it manages the whole flow.
- **Choreography**: services react to each other's events, with no boss. Good for simple flows with few services.

The workflow above is an orchestrator (ours).
</Step>

<Step id="fails" name="When compensation fails" tag="PROBLEM">
Compensations can fail too. Plan for it:

- Make each one **idempotent**, so it can be repeated safely.
- **Record progress**, so you can resume where it stopped.
- If nothing works, **alert a person**. Sometimes manual intervention is the only fix.

Compensation doesn't have to run in reverse order, and a refund isn't the same as never charging.
</Step>

<Step id="gap" name="Wrong for a moment" tag="TIP">
Between the failure and the compensation, the data is briefly wrong: the customer is charged for an order that won't ship (ours).

If that's unacceptable, a saga is the wrong tool.
</Step>

<Step id="when" name="When to use it">
**Use it** when one business operation spans several services and must be undone if a later step fails.

**Skip it** when the transactions are tightly coupled, when compensations would have to run in earlier steps, or when services depend on each other in a cycle (the Microsoft Learn docs list these three). If you can't tolerate even brief inconsistency, a saga is the wrong tool (ours).
</Step>

<Step id="recap" name="Recap" tag="RECAP">
- Across systems there's **no rollback**: compensate instead.
- A **saga** is small steps plus an undo for each.
- Steps are **compensable**, **pivot** or **retryable**.
- In Logic Apps: a Try scope, a Catch scope, and recorded progress (ours).
- Compensations must be **idempotent**, resumable and backed by an alert.
</Step>
